# Правила работы Codex

## Перед началом работы

- Перед первой правкой прочитать `AGENTS.md`, `docs/README.md`, `docs/journal.md` и `docs/open-questions.md`.
- Если задача относится к отдельному направлению, читать только относящиеся к нему `spec` и `plan`.
- Уже принятое решение не открывать заново без причины.
- Если свежая запись в `docs/journal.md` противоречит старому документу, более новая запись считается актуальнее.

## Работа с файлами и сессиями

- Перед изменением существующего документа перечитать его с диска непосредственно перед записью.
- Не записывать файл из старой копии, если он мог измениться после чтения.
- Не допускать параллельную запись одного и того же служебного документа из разных сессий, особенно `docs/journal.md`.
- Законченные сессии Codex не оставлять открытыми как источник старых копий файлов.
- Перед удалением, перезаписью значимого файла или опасной Git-командой сначала получить разрешение автора.

## Секреты

- Секреты не писать в код, Git, документацию, сообщения коммитов или сохраняемые промпты.
- Локальные секреты хранить только в `.env`-файле, исключённом через `.gitignore`.
- В документации разрешено хранить только названия переменных, например `OPENAI_API_KEY`, но не их значения.

## Где хранить сведения

- Принятое решение и его причину записывать в `docs/journal.md`.
- Нерешённый вопрос, осознанную заглушку или недоделку записывать в `docs/open-questions.md`.
- Идею без спецификации записывать в `docs/ideas.md`.
- Для нового крупного направления создавать `docs/<направление>-spec.md` и `docs/<направление>-plan.md`, а также добавлять их в `docs/README.md`.
- У каждого решения должно быть одно основное место хранения.

## Оценки и реализация

- До реализации новой функциональности давать приблизительную оценку времени разработки и регулярной стоимости.
- Для API по возможности считать стоимость на единицу работы и на типичный объём.
- Если точная стоимость неизвестна, явно фиксировать её как неизвестную.
- Не усложнять архитектуру без необходимости.
- У новой зависимости или внешнего сервиса должна быть понятная причина.
- Наличие Vercel или OpenAI API не означает обязательного использования.
- Код не считается готовым только потому, что написан: выполнять доступные проверки.

## Общение и Git

- Общаться с автором на русском языке.
- Служебную документацию и комментарии в коде писать на русском языке.
- Сообщения коммитов писать на беларускай в формате `вобласьць: што зроблена`.
- После каждого коммита выполнять `git show --stat HEAD` и проверять, что в коммит вошли только ожидаемые файлы.
